## Confirmed defect: browser API routing through Hubitat Remote Admin

### Root cause

JimB's scan-start failure is now confirmed and reproducible.

When Automation Map is opened locally, the browser-facing API URL generated by `getLocalURL()` is reduced to a relative path such as:

    /apps/api/2929/scan?access_token=...

That works when the Hubitat administration page itself is being served by the hub, because the relative URL resolves against the hub origin.

JimB was instead using Hubitat Remote Admin:

    https://remoteaccess.aws.hubitat.com/installedapp/configure/2929/main

The browser therefore resolved the relative scan path as:

    https://remoteaccess.aws.hubitat.com/apps/api/2929/scan

Remote Admin does not serve Automation Map's OAuth endpoint at that path. It returned HTTP 200, `text/html`, with a 404/session-expired page. Versions 1.8.5 through 1.8.7 then attempted to parse that HTML as JSON and surfaced the generic:

    Unexpected token '<', "<!DOCTYPE" ... is not valid JSON

Version 1.8.8 exposed the actual responder and URL, proving the failure never reached Automation Map's `/scan` mapping.

The initial installation scan still completed successfully because `installed()` calls `startScan()` internally on the hub. It does not traverse the browser `/scan` OAuth endpoint. Production v1.2.1 reproduces the same Remote Admin failure, so this is not Dev-specific.

### What is ruled out

The confirmed cause clears the earlier competing hypotheses as primary causes:

- browser-specific behaviour;
- Pixel/Android networking;
- firmware 2.5.1.152;
- the scan engine itself;
- a Dev-only regression;
- a `startScan()` exception;
- OAuth installation configuration as the root cause;
- Hub Login Security as the root cause.

The defect is architectural: Automation Map assumes the browser UI origin is also the Automation Map API origin.

# Specification: local and remote API endpoint routing

## 1. Objective

Make every Automation Map browser-to-app request independent of the origin from which the Hubitat administration UI is being viewed.

Automation Map must work when the user accesses the hub:

- directly over the LAN;
- using a local hostname;
- through a VPN that can reach the LAN;
- through Hubitat Remote Admin.

The solution must preserve local operation when Internet access is unavailable.

## 2. Architectural principle

**Do not derive Automation Map's API destination from `window.location.origin`.**

The Hubitat administration UI origin and the Automation Map OAuth API origin are separate concerns.

Automation Map must explicitly support two API routes:

1. **Local API route** - used when the browser is directly addressing the hub.
2. **Cloud API route** - used when the browser is viewing the administration UI through Hubitat Remote Admin.

A simple absolute LAN URL is not sufficient. A remote browser normally cannot route to an RFC1918 address such as `192.168.x.x`, and an HTTPS Remote Admin page fetching an HTTP LAN URL may also be blocked as mixed content or cross-origin traffic.

The correct remote target must therefore be Hubitat's cloud-facing OAuth API endpoint, not the hub's LAN address and not the Remote Admin portal path.

## 3. Non-goals

This change must not:

- attempt to tunnel an RFC1918 address through Remote Admin;
- assume Remote Admin proxies arbitrary `/apps/api/...` paths;
- make LAN scanning dependent on Hubitat cloud services;
- send the Hubitat administrator session cookie with Automation Map OAuth requests;
- expose the OAuth token in logs, UI diagnostics or screenshots;
- change the scan engine;
- change the graph schema.

## 4. Central endpoint abstraction

The current helper is local-only in intent and returns a relative path:

```groovy
String getLocalURL(String fileName) {
    String fullURL = "${fullLocalApiServerUrl}/${fileName}?access_token=${state.accessToken}"
    return (fullURL =~ URL_PATTERN).findAll()[0][1]
}
```

Replace this single-route assumption with a central endpoint abstraction.

Preferred conceptual interface:

```groovy
String getLocalApiURL(String endpoint)
String getCloudApiURL(String endpoint)
```

or:

```groovy
Map getApiURLs(String endpoint)
```

returning:

```groovy
[
    local: '<absolute or intentionally local endpoint>',
    cloud: '<absolute Hubitat cloud OAuth endpoint>'
]
```

The cloud URL must come from Hubitat's own runtime URL-generation mechanism. It must not be hand-built from guessed hostnames or path formats.

Before implementation, verify which Hubitat runtime property supplies the cloud counterpart to `fullLocalApiServerUrl` on the supported firmware. A likely candidate is `fullApiServerUrl`, but this must be confirmed empirically rather than assumed.

Every browser-accessible endpoint must use this abstraction:

- `/scan`
- `/scan-status`
- `/automation-map.html`
- `/externals`

There must be no second implementation elsewhere that manually assembles `/apps/api/...` URLs.

## 5. Client-side API configuration

Render the available API URLs into the page as explicit configuration rather than deriving them from the page origin.

Conceptually:

```javascript
const AM_API = {
    scan: {
        local:  '...',
        cloud:  '...'
    },
    status: {
        local:  '...',
        cloud:  '...'
    },
    map: {
        local:  '...',
        cloud:  '...'
    },
    externals: {
        local:  '...',
        cloud:  '...'
    }
};
```

The client selects the route explicitly.

Initial Remote Admin detection can be:

```javascript
function amUsingRemoteAdmin() {
    return window.location.hostname === 'remoteaccess.aws.hubitat.com';
}
```

and:

```javascript
function amEndpoint(routes) {
    return amUsingRemoteAdmin() ? routes.cloud : routes.local;
}
```

This detection decides **which API route to use**, not whether functionality is available.

Do not permanently scatter checks for `remoteaccess.aws.hubitat.com` through the code. Keep Remote Admin detection in one helper so additional Hubitat remote origins can be supported later.

## 6. Local behaviour

When Automation Map is opened directly from the hub, continue using the local API route.

Requirements:

- no cloud round trip;
- no Internet dependency;
- current scan scheduling semantics preserved;
- `credentials: 'omit'` retained for OAuth calls;
- access token remains the authentication mechanism.

The existing `credentials: 'omit'` is load-bearing. Sending the Hubitat UI session cookie previously caused scan scheduling to occur inside the UI transaction, after which `runIn()` did not reliably survive. Do not reverse that behaviour as part of the Remote Admin fix.

## 7. Remote Admin behaviour

When the page is being viewed through:

    remoteaccess.aws.hubitat.com

the browser must not request:

    https://remoteaccess.aws.hubitat.com/apps/api/<id>/scan

Instead it must call the absolute Hubitat cloud OAuth endpoint for that app instance.

Conceptual flow:

```text
Browser
   |
   | Remote Admin UI
   v
remoteaccess.aws.hubitat.com
   |
   | separate browser request to cloud OAuth API
   v
Hubitat cloud API
   |
   v
Automation Map /scan
   |
   v
startScan()
   |
   v
Hub
```

This replaces the broken flow:

```text
Browser
   |
   v
remoteaccess.aws.hubitat.com/apps/api/.../scan
   |
   v
Remote Admin 404 HTML
```

## 8. CORS validation - mandatory before committing to the design

The principal unresolved technical question is whether a Remote Admin page can use JavaScript `fetch()` to read the response from the Hubitat cloud OAuth endpoint.

The origins will differ:

```text
Page origin:
https://remoteaccess.aws.hubitat.com

API origin:
<Hubitat cloud OAuth API host>
```

The implementation must therefore verify the cloud endpoint's CORS behaviour.

### First probe

Use the read-only `/scan-status` endpoint before testing `/scan`.

From a Remote Admin page, test:

```javascript
fetch(CLOUD_SCAN_STATUS_URL, {
    credentials: 'omit',
    cache: 'no-store'
})
```

Success criteria:

- the request reaches the correct Automation Map instance;
- the OAuth token is accepted;
- the response is JSON;
- JavaScript is permitted to read the response;
- no Remote Admin proxy path is involved.

If this works, normal cloud routing is straightforward.

## 9. Fallback if cloud request succeeds but CORS blocks response access

Starting a scan is a command whose important effect is on hub state. The browser does not strictly need to inspect the HTTP response to know whether scanning subsequently started.

If Hubitat's cloud endpoint accepts the request but CORS prevents JavaScript from reading the response, evaluate an opaque request:

```javascript
fetch(CLOUD_SCAN_URL, {
    mode: 'no-cors',
    credentials: 'omit',
    cache: 'no-store'
});
```

The client would then:

1. show `Starting scan...`;
2. wait approximately 2 seconds;
3. reload the Remote Admin configuration page;
4. let the server-rendered page show `state.scanRunning`, scan progress or `state.scanError`.

This uses hub state as the confirmation channel instead of the cross-origin response.

Do not adopt this fallback unless a real cloud request proves it is required. A readable normal fetch remains preferable because it preserves meaningful diagnostics.

## 10. Map link

The same architectural defect can affect `View Automation Map` because it currently uses the same local/relative URL assumptions.

The map link must therefore use the same local/cloud endpoint abstraction.

Locally:

```text
local automation-map.html endpoint
```

Through Remote Admin:

```text
cloud automation-map.html endpoint
```

Fixing `/scan` alone would leave the core routing defect present elsewhere.

## 11. API calls made from the map page

Once `automation-map.html` is open, any API calls made by that page must also use explicit endpoint configuration.

This includes at least:

- `/scan-status`
- `/externals`

Do not allow the map page to fall back to constructing a relative `/apps/api/...` path from its current browser origin.

Prefer one generated API object and use it everywhere:

```javascript
fetch(API.status)
fetch(API.externals)
```

rather than re-synthesising endpoint URLs independently.

## 12. Security requirements

### OAuth token handling

The access token is a credential and must never appear in user-facing diagnostic output.

Version 1.8.8 currently reports the final response URL. Any permanent implementation must sanitise it before display because the API URL contains:

    ?access_token=<token>

Use origin plus pathname only:

```javascript
function safeUrl(raw) {
    try {
        const u = new URL(raw);
        return u.origin + u.pathname;
    } catch (_) {
        return '(unavailable)';
    }
}
```

The same sanitisation principle applies to any body preview in case an error page echoes the requested URL.

Never expose the access token in:

- UI errors;
- browser diagnostics;
- logs;
- screenshots;
- community-thread troubleshooting instructions.

Continue using:

```javascript
credentials: 'omit'
```

for OAuth API requests.

## 13. Error handling

The 1.8.8 text-first diagnostic pattern should become permanent.

Do not return to unguarded:

```javascript
response.json()
```

for a response that may be intercepted by an authentication, routing or proxy layer.

Preferred behaviour:

1. read response as text;
2. capture HTTP status;
3. capture content type;
4. capture sanitised responder origin/path;
5. parse JSON explicitly;
6. if parsing fails, report what actually answered rather than the browser's generic parser exception.

Permanent diagnostics may include:

| Field | Include |
|---|---|
| HTTP status | Yes |
| Content-Type | Yes |
| Sanitised origin + pathname | Yes |
| Query string | Never |
| Sanitised short body prefix | Yes |
| Access token | Never |

The design rule is: **a response that might not be JSON must never reach a JSON parser before the raw response has been captured.**

## 14. Behaviour matrix

| Administration access path | API route | Expected result |
|---|---|---|
| Hub LAN IP | Local | Scan works locally |
| Hub local hostname | Local | Scan works locally |
| VPN with LAN reachability | Local | Scan works locally |
| Hubitat Remote Admin | Cloud | Scan works via cloud OAuth endpoint |
| Internet unavailable, LAN available | Local | Scan still works |
| Remote Admin, cloud API unavailable | Cloud | Clear remote API error |
| Invalid OAuth token | Local or cloud | Explicit authentication failure |
| HTML returned unexpectedly | Local or cloud | Diagnostic responder details, not `Unexpected token '<'` |

## 15. Implementation sequence

### Phase 1 - discover and verify Hubitat's cloud URL helper

On Dev only, expose or log sanitised versions of the local and cloud API server URLs supplied by the runtime.

Verify the actual cloud URL shape instead of assuming it.

### Phase 2 - prove `/scan-status` through Remote Admin

Generate the cloud `/scan-status` URL and call it from a Remote Admin page.

This is the critical architectural test because it proves:

- routing;
- OAuth;
- CORS/readability;
- correct app-instance targeting.

Do not change scan behaviour until this succeeds or its exact CORS limitation is understood.

### Phase 3 - route `/scan`

Use the cloud route through Remote Admin and the local route on LAN access.

Retain 1.8.8's text-first error handling.

### Phase 4 - route map and supporting endpoints

Apply the same routing abstraction to:

- `automation-map.html`;
- `/scan-status`;
- `/externals`.

### Phase 5 - normalise diagnostics

Remove JimB-specific diagnostic wording but keep the underlying status/content-type/sanitised-responder reporting as permanent hardening.

## 17. Preferred end-state

```text
                   +----------------------+
                   | Automation Map page  |
                   +----------+-----------+
                              |
                    Determine access mode
                              |
              +---------------+---------------+
              |                               |
            Local                         Remote Admin
              |                               |
              v                               v
   Hub local OAuth API              Hubitat cloud OAuth API
              |                               |
              +---------------+---------------+
                              |
                              v
                       Automation Map
                              |
                              v
                          startScan()
```

The fix is **not** "make the existing relative URL absolute".

The fix is to remove the assumption that there is one browser API route and introduce an explicit **local/cloud endpoint strategy**. An absolute LAN URL would solve only the local case and fail for the very remote scenario that exposed the defect.

## 18. Immediate next engineering action

Before writing the full routing change, answer one question empirically:

> From an Automation Map configuration page opened through Hubitat Remote Admin, can JavaScript call the app instance's absolute Hubitat cloud `/scan-status` OAuth endpoint and read the JSON response?

If yes, implement normal local/cloud endpoint selection.

If the request reaches the hub but response access is blocked by CORS, test the opaque-request + page-refresh fallback for `/scan` and determine separately how the map page and read endpoints should be exposed remotely.

## 19. 1.8.9 Remote Admin reproduction - Firefox/Android NetworkError

A further reproduction on Dev v1.8.9 confirms the same Remote Admin routing defect with a different browser-level symptom.

The Automation Map configuration page was visibly being served from:

    remoteaccess.aws.hubitat.com

Pressing **Scan relationships now** produced:

    Could not start the scan: NetworkError when attempting to fetch resource.

The existing graph remained available and showed the previous successful scan (`88 of 88 apps`, `301 nodes`, `1036 relationships`), which is consistent with the scan engine and stored graph being healthy. The failure occurs only when the browser attempts to initiate a new scan.

### Interpretation

This does not weaken the confirmed routing diagnosis. It shows that the exact user-facing error depends on the browser/network stack.

Earlier Remote Admin testing reached the wrong `remoteaccess.aws.hubitat.com/apps/api/...` destination and received an HTML response, which produced the `Unexpected token '<'` family of errors when parsed as JSON. In this Firefox/Android reproduction, `fetch()` fails before JavaScript receives a usable HTTP `Response`, so the promise rejects directly with the browser-generated `NetworkError when attempting to fetch resource` message.

Both symptoms are compatible with the same architectural fault:

```text
Remote Admin page origin
        |
        | relative /apps/api/... URL
        v
remoteaccess.aws.hubitat.com
        |
        X wrong API destination / browser fetch failure
```

The screenshot therefore provides additional evidence that the defect is not Hub Login Security, a failed OAuth installation, or a scan-engine exception. The browser request is being routed incorrectly before Automation Map's `/scan` mapping can become the relevant execution path.

### Engineering consequence

Do not add special handling for `NetworkError` as though it were a separate defect. The fix remains the endpoint-routing change specified above: browser requests made through Remote Admin must target Hubitat's cloud-facing OAuth API endpoint, while direct LAN administration must retain the local API route.

The permanent error handler should nevertheless preserve the distinction between:

- an HTTP response containing non-JSON content;
- an HTTP error response;
- a true `fetch()` rejection where no readable response object exists.

That distinction will make future proxy, CORS, DNS and routing failures diagnosable without conflating them with Automation Map application errors.

### Exact 1.8.9 Remote Admin URL confirmed

The exact configuration URL for this v1.8.9 reproduction is:

    https://remoteaccess.aws.hubitat.com/installedapp/configure/2976/main

This establishes the Automation Map app instance as **2976** and confirms the browser origin as `https://remoteaccess.aws.hubitat.com`.

With the current relative-path strategy, a browser-side request for `/apps/api/2976/scan?...` is therefore resolved against the Remote Admin origin, conceptually producing:

    https://remoteaccess.aws.hubitat.com/apps/api/2976/scan

That is the wrong destination: it addresses the Remote Admin web front-end rather than the Automation Map OAuth API endpoint for app instance 2976.

This concrete URL strengthens the diagnosis by removing ambiguity about the page origin and app instance. It also gives a specific acceptance-test instance for the routing fix: when the configuration page is opened through the URL above, pressing Scan must not generate a request to `remoteaccess.aws.hubitat.com/apps/api/2976/...`; it must select the Hubitat cloud OAuth API route for instance 2976.
